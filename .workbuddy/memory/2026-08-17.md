## 桥接层（任务3，已完成）

### 关键结论（踩坑）
1. **yazi 不需要 PTY**：用 `std::process::Command` + 分离管道（stdout piped / stderr null）即可。stdout 是**纯净的事件流**（每行一条），完全没有 ANSI 污染。相比 ConPTY/portable-pty 简单太多。
2. **`--client-id` 和 `ya emit-to` 的 receiver 必须是纯数字**（u64，如时间戳毫秒），不能是字符串。
3. 事件格式：`kind,receiver,sender,{json}`，逗号分隔 4 段；body 是 JSON（如 `cd` → `{"tab":1,"url":"D:\\"}`，`hover` → `{"tab":1,"url":"..."或null}`）。
4. 启动命令：`yazi --client-id <ts> --local-events cd,hover,rename,trash,delete,move,bulk`（cwd 用 current_dir 设置）。发指令：`ya emit-to <client_id> cd <path>`。

### 实现
- `src/yazi.rs`：`YaziClient`（spawn + 事件接收 channel + send 动作）、`YaziEvent` 枚举（Cd/Hover/Other）、解析器。
- `src/main.rs`：Root 视图持有 client/cwd/hovered/log；`cx.spawn` 异步轮询 channel → `weak.update` 更新视图；`nav_button` 测试发 cd 指令。
- `examples/yazi_probe_pipe.rs`：独立探针，验证事件流格式（保留作调试用）。

### GPUI 0.2.2 补充 API 坑
- `.on_click()` / `.overflow_y_scroll()` 是 `StatefulInteractiveElement` trait 方法，只对 `Stateful<Div>` 生效。`div()` 返回 `Div`，需先 `.id(...)` 转成 `Stateful` 再用（Zed 源码同款模式：`.child(...).id(ix).on_click(...)`）。
- 后台更新视图：`cx.spawn(async move |weak, cx| { weak.update(cx, |this, cx| {...}).ok(); }).detach()`。
- **链接报 LNK1104 无法打开 exe**：多半是旧进程还占着 exe 文件，先 kill 再重编。

### 验证
- `cargo build` 成功；`yazi-gui.exe` 运行，GUI 进程 + yazi 子进程（2 个）都存活，无 panic。

## 文件列表（任务4+5，已完成）

### yazi Lua 插件发布完整文件列表（关键踩坑）
1. **插件入口是 `main.lua`，不是 `init.lua`**。`init.lua` 是配置根目录的用户初始化文件。
2. **插件不会自动加载**：需在配置根 `init.lua` 里 `require("插件名"):setup()` 才触发插件 `setup`。插件 `main.lua` 返回 `{ setup = function(state, opts) ... end }`。
3. **`YAZI_CONFIG_HOME`** 环境变量可覆盖配置目录 → 把插件放项目 `assets/yazi/` 下，随 GUI 分发，不污染用户全局配置。
4. **`ps.pub(kind, value)` 能被 `--local-events=kind` 捕获**（本地发布即 stdout 事件）。`ps.sub("cd"/"hover", cb)` 订阅内部事件，回调在 sync 上下文可直接访问 `cx`。
5. 文件列表：`cx.active.current.files` 用 `ipairs` 遍历；每个文件 `.name`、`.cha`；cha 字段：`is_dir`/`is_hidden`/`is_link`/`len`(字节大小，**不是 length**)/`mtime`(Unix 秒浮点)/`atime`/`btime`。
6. 调试：`ya.err`/`ya.dbg` 需设 `YAZI_LOG=debug` 才写 `%APPDATA%\yazi\state\yazi.log`。

### 实现
- `assets/yazi/init.lua`：`require("gui-files"):setup()`。
- `assets/yazi/plugins/gui-files.yazi/main.lua`：`ps.sub("cd"/"hover")` → 发布 `gui-files`（cwd + files[{name,is_dir,is_hidden,size,mtime}] + hovered）。
- `src/yazi.rs`：新增 `FileEntry`、`GuiFiles` 事件；spawn 时设 `YAZI_CONFIG_HOME`、`--local-events=cd,hover,gui-files`。
- `src/main.rs`：渲染文件列表（目录蓝色带 `/`、文件带大小、悬停高亮），点目录进入、`上级` 按钮返回父目录。

### GPUI 0.2.2 补充坑
- `ElementId` 只实现 `From<&str>`/`From<SharedString>` 等，**不实现 `From<String>`**；且需 `'static`。动态字符串作 id 用 `.id(SharedString::from(s.clone()))`。

## UI 卡死 bug（已修复，重要坑）
- 现象：窗口「未响应」（UI 主线程被阻塞）。
- 根因：**GPUI `cx.spawn` 跑在「主线程」（foreground executor）上**（源码注释 "Spawns the future ... on the main thread"）。我在里面用了阻塞的 `std::sync::mpsc::Receiver::recv()`，把主线程卡死。
- 修法：改用 `tokio::sync::mpsc::unbounded_channel()` + `rx.recv().await`（非阻塞，yield 给执行器）。`UnboundedSender::send` 可从 std::thread 直接调（非阻塞）。
- 验证：`(Get-Process yazi-gui).Responding` → True。
- 教训：**凡是在 `cx.spawn` 里的异步任务，绝不能做阻塞 I/O（recv/read/Command::output 等）**；阻塞活要么用 `.await` 的异步版，要么丢到 `cx.background_executor().spawn()` 或独立 std::thread。
- 提交：`8d130bb`

## 悬停同步（已修复，关键点）

## 预览不触发 + tokio::fs 崩溃（已修复）
1. **预览不触发**：事件时序 bug——yazi 先发 `Hover` 事件（我更新了 `self.hovered`），紧接着发 `GuiFiles`（也带 hovered），而触发逻辑是"GuiFiles 里 hovered != self.hovered 才触发"，但 self.hovered 已被 Hover 抢先更新，永远判"无变化"。修法：抽 `set_hovered()` 统一去重+触发，Hover/GuiFiles 都走它。
2. **tokio::fs::read 崩溃**：`cx.spawn` 跑在 GPUI 自定义前台执行器（**不是 tokio runtime**），`tokio::fs::read` 需要 reactor → panic "no reactor running"。修法：`cx.background_executor().spawn(async { std::fs::read(...) }).await`（后台执行器是 tokio，Task 实现 Future 可 await）。
- 教训：`cx.spawn` 里能用 `tokio::sync::mpsc/oneshot`（channel 不需要 reactor），但不能用 `tokio::fs`/`tokio::time` 等需要 reactor 的 API；阻塞/文件 I/O 丢给 `background_executor().spawn` 或 std::thread。
- 提交：`fc81d53`

## trash 在 GPUI 后台线程崩溃（已修复，含二次踩坑）
- 现象：点「删除」→ `trash` crate 在 `CoInitializeEx` panic："无法在设置线程模式后对其加以更改"（0x80010106 RPC_E_CHANGED_MODE），进程 abort。
- 根因：`trash::delete` 跑在 GPUI 后台执行器（tokio 线程）上，该线程已被 GPUI 的 windows 平台初始化为 **MTA**，trash 默认用 STA（`coinit_apartmentthreaded`）再初始化就冲突。
- **真正的坑（第二次闪退的原因）**：trash 的 `coinit_apartmentthreaded` 和 `coinit_multithreaded` 是**互斥 feature**，而 `default = ["coinit_apartmentthreaded", "chrono"]`。若只写 `features = ["coinit_multithreaded"]` 而不关默认，两个分支都编译，`init_mode` 先赋 MTA 又被 STA 覆盖，等于没改，仍然 panic。
- 正确修法：`trash = { version = "3", default-features = false, features = ["coinit_multithreaded"] }`。
- 验证：写 `examples/trash_probe.rs`——用 `CoInitializeEx(MTA)` 模拟后台线程再调 `trash::delete`，确认不 panic 且文件进回收站。FFI 声明在 Rust 2024 下要写 `unsafe extern "system"`。
- 提交：`fada084`（首次，不完整）→ `88f2e42`（default-features=false，真正修复）

## 重命名/新建（任务7 输入框，已完成）
- GPUI 无开箱即用 TextInput（那是 Zed ui crate 的），只有底层 `EntityInputHandler`（需实现 7 个方法 + 自定义 Element paint 里调 `window.handle_input`，太重）。
- 简单输入框用 **`on_key_down` + 手动字符串缓冲区** 即可：
  1. `Root` 实现 `Focusable`（`focus_handle` 字段用 `cx.focus_handle()` 创建，`focus_handle(&self,_cx)` 返回 clone）。
  2. 根 div 加 `.id("root").track_focus(&focus_handle).on_key_down(cx.listener(...))`。
  3. 进入输入模式时 `cx.focus_self(window)`（聚焦 Root）→ 键盘事件沿焦点路径分发到根 div 的 on_key_down。
- 键盘分发机制（源码 window.rs `dispatch_key_event`）：`focus_node_id_in_rendered_frame(focus)` → `dispatch_path` → `dispatch_key_down_up_event` 沿路径触发 `key_listeners`（即 div 的 on_key_down）。所以 **on_key_down 只在元素处于焦点路径时触发**。
- `Keystroke` 结构：`key: String`（"a"/"enter"/"escape"/"backspace"/"space"，字母统一小写）、`key_char: Option<String>`（实际输入字符，shift 大写）、`modifiers`。空格键 key 值是 "space" 不是单字符。
- 文件操作确认：Rust 直接 `std::fs::rename/write/create_dir_all` + `cd` 刷新 yazi（同删除）。
- **已知限制**：`on_key_down` 拿不到 IME 中文输入（key 是 ASCII 等价、key_char 可能 None），中文文件名需后续升级 `EntityInputHandler`。
- 提交：`22a45ce`
